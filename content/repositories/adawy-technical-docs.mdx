# `adawy-technical-docs`

**This handbook.** The department's single source of truth: what we build, why
we build it, and how we work.

Public · Nextra 4 (Next.js docs framework) · npm

It is public by decision ([ADR-007](/architecture/adrs)) — onboarding is
self-serve, docs rot is visible in git, and the handbook itself demonstrates
the standards it describes. It is **English-only** by decision too, for the
reasoning in that same ADR.

## Running it

This is the smallest repo in the org and the best first clone — if it builds
locally, your toolchain is correct.

```bash
git clone git@github.com:Adawy-Group/adawy-technical-docs.git
cd adawy-technical-docs
npm install
npm run dev                    # http://localhost:3000

node scripts/check-links.mjs   # CI runs this FIRST — it needs no build
npm run build                  # the real gate on content
```

<Callout type="warning">
  This repo uses **npm**, not pnpm. It is standalone and has no workspace, so
  it keeps a `package-lock.json`. `adawy-platform` is the pnpm one — check
  which repo you are in before installing.
</Callout>

## Layout

```
app/                  Nextra app shell ([[...mdxPath]] catch-all + layout)
content/              every handbook page (MDX) — the sidebar mirrors the folders
  <section>/_meta.ts  sidebar order and titles for that section
components/           the site's own MDX components + the JSON-LD helper
lib/seo.ts            metadata, canonicals, structured data
scripts/check-links.mjs   the link, anchor and sidebar checker
next.config.mjs       Nextra config
mdx-components.tsx    the MDX component map — a component missing here is undefined
```

## Adding or changing a page

<Steps>

### Create the `.mdx` file

In the right section folder under `content/`. Frontmatter carries `title`,
`description` and `tags`:

```mdx filename="content/standards/example.mdx"
---
title: Example Standard
description: One sentence — it feeds the meta description and the search index.
tags: ['Reference', 'Daily']
---
```

`tags` render as pills in the page header strip. Keep to **two or three**,
drawn from the vocabulary already in use — a tag that appears on one page is a
label, not a tag.

### Add it to `_meta.ts`

The filename key, with its display title. **A page missing from `_meta.ts` does
not appear in the sidebar**, and `check-links.mjs` fails on it.

Keep the flat `export default { key: 'Title' }` shape at two-space indent: the
checker parses these files textually with a regex rather than importing them,
so unusual formatting produces false failures.

### Run both gates

```bash
node scripts/check-links.mjs
npm run build
```

In that order — the checker needs no build output, and a broken link should be
reported even when a page fails to prerender.

### Open a PR

Vercel posts a preview URL; merging to `main` deploys. A documentation fix
needs no Trello card ([why](/onboarding/first-pr)).

</Steps>

Every page has an **"Edit this page on GitHub"** link in its footer. If
something here is wrong, that link is the shortest path to fixing it.

## Page conventions

- **Every page carries `title`, `description` and `tags`**, and
  `check-links.mjs` fails without them. The description feeds both the meta
  description and the search index, so a page missing one ranks badly in the
  site's own search. A page that teaches or explains opens its tags with its
  [Diátaxis](https://diataxis.fr/) mode — `Tutorial`, `How-to`, `Reference`
  or `Explanation` — because a reader who wants to *do* a thing and a reader
  who wants to *understand* it need different pages. The repository pages are
  the deliberate exception: they open with their world (`Group work`,
  `Client work`, `Internal`), which is the first thing anyone needs from them.
- **Draw a diagram; do not take a screenshot.** There is not one screenshot in
  this handbook, and that is a decision. A picture of the Trello board or a
  Vercel dashboard is correct on the day it is pasted and silently wrong after
  the next UI change — the same failure the derived dates below exist to
  prevent, except no build warns about it and nobody re-opens an image to check
  it. A ` ```mermaid ` fence is diffable, greppable, reviewable in a PR, and
  wrong only when the *process* changes, which is a change somebody is already
  editing this page for. A wide left-to-right flowchart **scrolls inside its own
  box** rather than shrinking to the column: Mermaid renders at `width="100%"`,
  which had been scaling the git-workflow diagram from 2284px down to 670px and
  28px tall, with every label far below readable size. `app/globals.css` puts a
  floor under it.
- **State the reason.** Every rule in this handbook says *why* it exists. A
  rule without a reason is a candidate for deletion; that is the house style,
  not a formality.
- **Link across sections with absolute paths** (`/standards/coding`), not
  relative ones. `check-links.mjs` validates `](/…)` and `href="/…"`; a
  relative link silently skips validation and can 404 in production with a
  green build.
- **Mermaid diagrams** render from ` ```mermaid ` fences. Break a node label
  with `<br/>`, never a literal `\n` — this build drops the escape instead of
  breaking the line, and the label renders run together.
- **Numbers must be stable.** Repository counts, locale counts, founding years
  and committed targets are fine. Commit counts, deploy counts and last week's
  Lighthouse score are not — nothing here refreshes them, and a stale number is
  a page lying with more confidence than prose can.

### What is derived, and must not be hand-written

| Shown | Comes from |
| ----- | ---------- |
| "6 min read" | `readingTime: true` in `next.config.mjs`, computed from the compiled MDX |
| "Updated 22 Aug 2026" | The file's last git commit |
| "Last updated on …" in the footer | The same timestamp, rendered by the theme |

Writing any of those into a page by hand produces a number that goes stale with
nothing failing.

<Callout type="important">
  **Both git-derived dates need full history, and two different clones have to
  provide it.** CI checks out with `fetch-depth: 0`. The Vercel build is a
  *separate* clone and is shallow by default, which needs **both** of these:

  1. **`VERCEL_DEEP_CLONE=1`** in the Vercel project's environment variables.
     This is the supported switch and the one that always works.
  2. **`scripts/unshallow.mjs`**, which runs as `prebuild` and deepens the
     clone itself. It is the belt to that braces — useful anywhere the project
     is built outside Vercel, and a no-op on a complete clone.

  Without full history a page reports a date from before it existed, which is
  worse than no date at all: a wrong timestamp reads as a page somebody
  maintains. The script never fails the build; if it cannot reach the remote it
  logs `[unshallow] skipped` and the dates degrade rather than the deploy
  failing.

  **To check which applies, read the deploy log** for the `[unshallow]` line.
  The tell-tale on the site itself is a page whose date is *newer* than its last
  real change — that means every page is falling back to `HEAD`.
</Callout>

## Components available in MDX

All registered globally in `mdx-components.tsx` — use them without an import.
**A component used in MDX but missing from that map compiles to `undefined`.**

**From Nextra:** `Callout`, `Cards`, `FileTree`, `Steps`, `Tabs`, `Bleed`.

**This site's own:**

```mdx
<Badge tone="group">Group</Badge>

<Stats>
  <Stat value="8" label="repositories" hint="in the org" />
</Stats>

<Checklist id="unique-storage-key">
  <Task>Something to tick</Task>
</Checklist>
```

| Component | For | Notes |
| --------- | --- | ----- |
| `Badge` | A status or classification, inline | `tone`: `group`, `client`, `internal`, `live`, `building`, `holding`, `planned`, `private`, `public`, `neutral`. A closed set, so one meaning always gets one colour |
| `Stats` / `Stat` | A row of at-a-glance numbers | **Stable facts only** — see above |
| `Checklist` / `Task` | A list worked through over hours or days | Ticks persist in the reader's own `localStorage` under `id`, and go nowhere else. Give every checklist a unique `id` |
| `Tabs` | The same procedure per repo or per package manager | `storageKey` syncs the reader's choice across the whole site |
| `Bleed` | A diagram wider than the prose column | |

`Callout` takes `type="info" | "warning" | "error" | "important"`, or no type
for a neutral tip. Pick by what the reader loses by skipping it:

| Type | Use for |
| ---- | ------- |
| *(none)* | A helpful tip — nothing breaks if it is missed |
| `info` | Scope or context that prevents a misreading |
| `important` | Something they must do, or CI fails |
| `warning` | A trap that costs real time or money |
| `error` | A risk with a silent or expensive failure mode |

**Keep a blockquote for actual quotations** — brand statements, taglines, and
lines quoted from another document. A callout is an aside from the page to its
reader; a blockquote is someone else speaking.

<Callout type="important">
  **A new component must be registered in `mdx-components.tsx` and documented
  in the table above**, or the next person will not know it exists. Keep it a
  server component unless it genuinely needs state — a `"use client"` component
  in the map costs every page that imports it, and this site's whole argument
  is that less JavaScript is the cheapest win there is.
</Callout>

## What CI runs

`.github/workflows/verify.yml`, in this order:

1. **`node scripts/check-links.mjs`** — every internal link, every `#anchor`
   (including same-page ones), every `href` on a card, and every page's
   presence in its `_meta.ts`. It runs first because it needs no build output.
2. **`npm run build`** — the real gate on content: a page can render in
   `npm run dev` and still fail to prerender.

`.github/workflows/external-links.yml` runs weekly and on demand:

3. **`node scripts/check-links.mjs --external`** - requests every off-site URL
   on the site and fails if one is gone. It is deliberately *not* in the PR
   gate: it needs the network, and a third party being briefly down would fail
   a branch that changed nothing. Weekly, a failure means "a link now points at
   nothing" rather than "your branch is broken". `localhost` URLs are skipped —
   they are instructions to the reader, not destinations.

## Who reviews a change

`.github/CODEOWNERS` routes every pull request. Ownership lives in that one
file rather than an `owner:` field on each page: at the department's current
size every page resolves to the same person, so the field would be 52 copies of
one fact, and a frontmatter owner is a claim nothing enforces while CODEOWNERS
actually requests the review. When review becomes peer-based
([code review](/how-we-work/code-review)), sections get their own lines there
and no page needs editing.


## Known traps

| Symptom | Cause | Fix |
| ------- | ----- | --- |
| Build fails with `Invalid input: expected nonoptional, received undefined → at children` on every page | A newer `zod` got hoisted; Nextra 4.6's `Layout` validates props against older `z.custom` behavior | Keep the `overrides.zod` pin in `package.json`, then `npm install` again |
| A page renders in dev but fails `next build` | A prerender error in MDX — unsupported syntax or a broken import | Open the failing route in dev; it shows the real message that the production build hides |
| A new page is missing from the sidebar | No entry in that folder's `_meta.ts` | Add the filename key with its title. `check-links.mjs` catches this |
| A component renders as nothing | It is used in MDX but not registered in `mdx-components.tsx` | Add it to the map |
| A Mermaid diagram renders as a code block or an error box | Syntax error inside the diagram | Validate at mermaid.live, then paste back |
| Every Mermaid diagram shows *"Expecting NEWLINE, got SPACE"* locally, but the deployed site is fine | Your working copy has CRLF line endings. The bundled Mermaid does not treat a lone CR as a line terminator | `.gitattributes` checks the repo out as LF everywhere; if you cloned before it existed, re-clone or run `git add --renormalize .` |
| A multi-line node label renders as one run-on line | A literal `\n` inside the label | Use `<br/>`. This Mermaid build drops `\n` instead of breaking the line |
| Search returns nothing in `npm run dev` | The Pagefind index is built by `postbuild` | Expected — run `npm run build` to populate it |

## Search

`npm run build` runs a `postbuild` step that indexes the site with
**Pagefind** into `public/_pagefind`. Search is therefore only populated after
a full build — an empty search box in `npm run dev` is expected, not a bug.

Two things make the index actually useful, and both are the author's job: an
`H2` per topic and an `H3` per subtopic, and sections that still make sense
when a search result drops the reader into the middle of a page. "The rule
above" is invisible to search; name the thing.
