# Performance Checklist

Everything here is measured on **throttled mobile**, because the audience loads
pages on Egyptian 4G. The old WordPress site scored ~32; every item below
traces to a documented cause of that score.

## The numbers, and which one blocks a merge

Three numbers appear in this handbook, and they are not alternatives — they are
a floor, a target and an ambition. Only one of them stops a pull request.

| Number | What it is | Who it binds |
| ------ | ---------- | ------------ |
| **≥ 90** | **The merge bar.** Lighthouse mobile, on the preview URL | Every page, every PR — this is the one that blocks |
| **94** | The launch target for a site going live | The launch quality gate ([new brand](/guides/launch-new-brand), [client launch](/how-we-work/client-projects#launch-checklist)) |
| **95+** | Sustained, at platform maturity | A direction, not a gate |

*Why a floor below the target:* a merge bar set at the launch target turns
every ordinary PR into a performance negotiation, and the first response to
that is people stopping measuring. A floor that is genuinely hard to breach
accidentally, plus a target enforced once at launch, catches the same
regressions and gets run.

Core Web Vitals sanity, at any of the three: **LCP &lt; 2.5s, CLS &lt; 0.1,
INP &lt; 200ms.**

### When the composite score cannot be the gate

[`jumeira`](/repositories/jumeira) is the standing exception, and the shape of
it is reusable. Lab runs of a page that is one pinned film swing about ten
points around an LCP heuristic, so a merge bar on the composite score is a coin
toss. Its Lighthouse CI therefore reports **performance as a warning** and puts
the *errors* on things that do not swing:

| Asserted as an error | Why it does not swing |
| -------------------- | --------------------- |
| Per-type transfer size — document, stylesheet, script, font, image | Bytes are bytes. A regression here is a real regression, every run |
| Total blocking time | Main-thread work, not a modelled paint |
| Cumulative layout shift | Deterministic for a given layout |
| Largest contentful paint, as a ceiling well above the target | Catches a collapse, ignores the noise |

Accessibility stays a hard error at 90; SEO is switched off entirely while the
site ships `noindex` before launch, because the one failing audit is the
publishing switch working
([client projects](/how-we-work/client-projects#the-go-live-switch)).

*The generalization:* **assert the inputs, warn on the score.** A budget on
transferred bytes fails the PR that added the bytes; a budget on a composite
score fails whichever PR happened to run on a noisy machine, and the first
response to that is people ignoring the check.

<Callout type="warning">
  **A score can also have a floor you cannot code your way under.** Measured on
  `jumeira` by blocking scripts at the audit and re-scoring: its own client code
  is worth about **4 points**, the fonts **3**, and **React's arrival on the
  page 20** — the same route scores 100 with all JavaScript blocked. Its Arabic
  route also sits about ten points below its English one on identical scripts,
  and that gap is font bytes an Arabic page genuinely needs. Before treating a
  score as a bug, find out what the page costs with all JavaScript blocked —
  otherwise you are optimising against a constant.
</Callout>

## Before you open the PR

- [ ] **Images** through `next/image` — WebP/AVIF, responsive `sizes`,
      explicit width/height (no layout shift). No `-scaled.jpeg` uploads, ever
      again.
- [ ] **Video** used decoratively: ≤1080p (720p is fine for a background
      loop), poster frame, `preload="none"`, starts after paint, respects
      `prefers-reduced-motion`. Long term: video CDN (Cloudflare Stream/Mux),
      not files served from the app.
- [ ] **Below-the-fold images are deferred by something that knows the
      finished layout** — see [the trap below](#lazy-loading-is-read-against-the-parse-time-layout).
- [ ] **Client JavaScript** — is each `"use client"` boundary necessary?
      Server Components for static-heavy pages; dynamic-import anything heavy
      and below the fold.
- [ ] **Fonts** — self-hosted via `next/font`, subsetted; Arabic and Latin
      loaded only where used.
- [ ] **Third-party scripts** — every one is a performance tax; each needs a
      reason, and analytics loads after interaction/idle.

### Lazy loading is read against the parse-time layout

**`loading="lazy"` defers by position, and the position it reads is the one the
*parser* has** — before any pin spacer, sticky hold or scene has been built. A
section that sits twelve viewports down in the finished document can be about
one viewport down at the moment the browser decides, and every image in it is
fetched on load.

Measured on `jumeira`'s production alias: nine images, 158,978 bytes, every one
requested between 272 ms and 297 ms — **before hydration had run at all.** CI
failed `resource-summary:image:size` at 204,148 bytes against a 153,600 budget,
and it had been over the line for a full release without failing, because one of
the three audit runs was blocked badly enough to fetch only four of them and the
assertion takes the best run.

Two things follow:

- **"It is far down the page" is not an exemption; it is the trap.** Deferring a
  section's own build to a gesture makes it *worse*, because at parse time the
  section is nearer the top than it will ever be again.
- **Defer with something that knows the real layout.** Run `getImageProps` so
  the optimiser still computes the candidate set, park the URL and `srcset` on
  attributes the browser does not fetch, and set them from an
  `IntersectionObserver` a couple of viewports out. **Arm them before any
  `prefers-reduced-motion` guard** — a section's photographs are the section,
  not an effect on it.

## Verify

- [ ] `pnpm build` (or `pnpm turbo build --filter=<app>`) then check the
      route-size output — a page that jumped in JS weight needs an explanation
      in the PR.
- [ ] Lighthouse (mobile, throttled) on the preview URL, against
      [the numbers above](#the-numbers-and-which-one-blocks-a-merge).
- [ ] Core Web Vitals within the thresholds above.
- [ ] **Measure media with the network panel, not Resource Timing.**
      `performance.getEntriesByType` does not surface media range requests, so
      it reports 0 bytes for a video and looks fine while the page is pulling
      megabytes. That mistake shipped a 6.8 MB preload in
      [`jumeira`](/repositories/jumeira) once already. Its films are frame
      sequences now, which Resource Timing *does* see — but the habit is the
      one worth keeping, because the panel is the only thing that shows you the
      order requests actually went out in.

## After deploy

- [ ] Watch Vercel Analytics / PageSpeed for the affected routes — the score
      moving is the proof, not the technique.
- [ ] A performance regression on a shared component is a platform incident,
      not a brand bug: it just shipped to every site at once.
