# Tech Stack & Why

Every tool here was chosen for a reason, and the reasons matter more than the
names. The governing principle: **choose tools the group owns and controls,
avoiding subscription dependencies that compound at 110-brand scale.**

## Built, decided, deferred — read this first

A stack page that lists chosen tools alongside running ones teaches a new
engineer to expect things that are not there. Everything below carries one of
these states, and nothing on this page is in a fourth one.

| State | Means | Where you will find it |
| ----- | ----- | ---------------------- |
| <Badge tone="live">Running</Badge> | In a repository today, in production or in CI | Clone it and it is there |
| <Badge tone="planned">Decided</Badge> | Chosen in advance so it is not re-litigated — **not installed** | An ADR or this page, and nowhere in a `package.json` |
| <Badge tone="building">Deferred</Badge> | Deliberately postponed, with a stated revisit trigger | The ADR that deferred it |

<Callout type="info">
  **Frontend is built; everything behind it is decided but not built.**
  Everything in the Frontend table is running today. The Backend and
  Platform-services tables are choices recorded in advance for Phases 2 and 3 —
  **nothing in the org currently runs NestJS, Prisma, Better Auth, Meilisearch,
  Redis, pgvector, Sentry or Better Stack.** Recording them early is deliberate;
  going looking for them in a clone is not.
</Callout>

## Frontend

| Layer | Choice | Why |
| ----- | ------ | --- |
| Monorepo | **Turborepo + pnpm** — `apps/` per brand + eight shared `@adawy/*` packages (`ui`, `design`, `motion`, `i18n`, `site`, `holding`, `eslint-config`, `typescript-config`) | One PR ships a shared fix to every brand; only affected apps rebuild; each brand still deploys independently |
| Framework | **Next.js 16 + TypeScript** | Performance built in, first-class Vercel deployment per app, and three years of production experience on the team. Note: middleware is `proxy.ts` in this version |
| Styling | **Tailwind CSS v4 + shadcn/ui** (`@adawy/ui`, `@adawy/design`) | Tokens are CSS-first (`@theme`): `@adawy/design` defines the token structure, each brand overrides the values — accessible, owned by the team, no component library subscription |
| Motion | **GSAP + Lenis** (`@adawy/motion`) | The brand guidelines require cinematic, scroll-driven motion; GSAP is the industry standard and Lenis provides smooth scrolling, driven by GSAP's ticker so they share one clock. Wired once in `@adawy/motion` — the package ships primitives, brands own choreography |
| 3D | **three.js**, plus **Rapier** for the physics playground | One WebGL context serves the whole page as a set of passes ([platform architecture](/architecture/platform-architecture)) |
| i18n | **next-intl** (`@adawy/i18n`) | `en` / `ar` / `fr` with RTL by design; locale routing and direction handling wired once, used by every brand |
| Forms | **React Hook Form + Zod** | Type-safe forms with one validation schema shared between client and server ([forms & enquiries](/guides/forms-and-enquiries)) |
| Transactional email | **Resend** | Contact and quote submissions; reached through a single delivery seam so the provider is swappable |
| Testing | **Vitest**, colocated | Pure logic is extracted specifically so it can be tested without a DOM ([testing](/standards/testing)) |
| Lint & format | **ESLint 9 (flat config) + Prettier**, both gating CI | `@adawy/eslint-config` machine-enforces the architecture — the rules in this handbook fail the build rather than waiting for a reviewer ([coding](/standards/coding#linting--formatting)) |

## What a client project is required to run

Client projects do **not** run "the same stack minus the monorepo". They run
the same **floor**, and vary above it — which is what
[ADR-010](/architecture/adrs) buys and what a shared package would have taken
away.

**The floor, in every client repo:** Next.js 16 App Router, TypeScript strict,
Tailwind v4, next-intl with real RTL, WCAG 2.1 AA, pnpm, Prettier, and a
publishing switch that keeps the site out of the index before launch.

**Above the floor, actual variation today:**

| Choice | Who differs, and why |
| ------ | -------------------- |
| Primitive library | `aladawy-pack` and `aladawy-shop` are on Radix; `jumeira` on Radix; `zad-alhkoul` and `adawy-group-links` on Base UI. Base UI is where new work starts — it is what `@adawy/ui` uses |
| Smooth scroll | Everyone pairs GSAP with Lenis, but not the same way. Most take it as a library; [`jumeira`](/repositories/jumeira#the-scroll-authority-is-a-reversed-decision) takes it through **Locomotive Scroll v5**, which is Lenis rebuilt, and pays for it by making **every** scrub on the page `scrub: true` — a numeric scrub under a smoothed wheel is two smoothings in series, and it reads as seek lag |
| Forms | Only the repos that take an enquiry carry react-hook-form + zod. A site with no form ships neither |
| State | `aladawy-shop` alone uses **Redux Toolkit**, justified by a quote that persists across routes and reloads. That is genuinely cross-cutting client state, and it is a project-specific choice, not a house pattern |
| Tests | Vitest in five repos; [`zad-alhkoul`](/repositories/zad-alhkoul) has none, which is a gap rather than a decision |

*Why state a floor instead of a stack:* a stack list goes stale the first time
a project makes a defensible different choice, and then the handbook is either
wrong or the project is "non-compliant" for no reason. A floor is a rule that
survives contact with the next brief — and every variation above it has to be
defensible, which is the actual standard.

## Backend <Badge tone="planned">Decided, not built</Badge>

| Layer | Choice | Why |
| ----- | ------ | --- |
| Runtime | **Node.js + NestJS** | One language across the whole platform; NestJS adds structure as the codebase grows |
| Database | **PostgreSQL + Prisma** | Open source; relational data and vector storage (pgvector) in one system — no separate vector DB |
| Cache & queue | **Redis (Upstash)** | Pay-as-you-go; sessions, rate limiting, caching, background jobs |
| Object storage | **Cloudflare R2** | S3-compatible with **no download fees** — members download brand asset packages constantly |

## Platform services <Badge tone="planned">Decided, not built</Badge>

| Service | Choice | Why |
| ------- | ------ | --- |
| Content | **In the repo** (MDX/config, reviewed via PR) | Site content is managed by the team in git for now; a CMS is a future decision, made when the content volume demands it |
| Search | **Meilisearch** (self-hosted) | Strong Arabic morphology support; no subscription |
| Authentication | **Better Auth** | Open source, multi-tenant, no per-user fees; user data stays in our database |
| AI | **Vercel AI SDK + Claude & Gemini APIs** | Provider-agnostic; Gemini leads on Egyptian Arabic, Claude on English business prose |
| Vector storage | **pgvector** | Same PostgreSQL database; no extra service at this scale |

## What we deliberately avoid (and why)

- **No hosted CMS (Contentful etc.)** — content lives in the group's own
  repositories and database; if a CMS is adopted later, it will be self-hosted.
- **No hosted auth (Clerk, Auth0)** — user data stays in our database, no
  per-user fees across 110 brands.
- **No Shopify / per-store commerce** — dozens of stores would compound into a
  significant subscription and operational burden; custom commerce on our
  stack has no vendor dependency and no revenue-tied fees
  ([ADR-005](/architecture/adrs)).
- **No dedicated vector database** — pgvector in the existing PostgreSQL.
- **No third-party analytics holding our user data** — Vercel Analytics on the
  frontend, self-hosted Metabase for internal dashboards.

> Every component is owned by the group except the few cloud services that
> genuinely cannot be self-hosted at this scale (Vercel for frontend hosting,
> Cloudflare for CDN). The group owns the code, the content, the user data,
> and the architecture.
