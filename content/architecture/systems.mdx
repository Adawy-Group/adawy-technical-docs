# Our Systems

This page covers **Adawy Group's own systems**. Software the department builds
for clients is a separate track with separate rules — see
[Client Projects](/how-we-work/client-projects) and
[ADR-010](/architecture/adrs).

## The unified platform (what we are building)

| System | What it is | Status |
| ------ | ---------- | ------ |
| **Brand sites platform** | One Turborepo monorepo: a thin Next.js app per Adawy brand — thirty-one today: `apps/group`, the studio's one-page site, five flagship holding pages (`pack`, `print`, `supplies`, `marketing`, `bizdev`) and twenty-four holding pages for the brands added in September 2026 — all on shared `@adawy/*` packages, each its own Vercel project; seven are on their own domains | <Badge tone="live">Built</Badge> Phase 1 |
| **The multi-tenant app** | One `apps/sites` mapping hostname → brand config, for the long tail ([ADR-008](/architecture/adrs)) | <Badge tone="planned">Decided, not built</Badge> |
| **Shared design system** | The ten `@adawy/*` packages: `ui` (shadcn primitives), `design` (Tailwind v4 tokens), `motion` (GSAP + Lenis), `i18n` (locales + direction), `site` (identity, routes, metadata), `holding` (the holding-page shell), `brand-app` (the holding-app shell), `analytics` (PostHog behind consent), plus `eslint-config` and `typescript-config`, which machine-enforce the rules the others assume | <Badge tone="live">Built</Badge> the most important technical deliverable |
| **Backend service** | Node.js (NestJS) in the same monorepo as `apps/api` ([ADR-009](/architecture/adrs)): authentication, business logic, Odoo integration, background jobs, real-time | <Badge tone="planned">Phase 2</Badge> first build of the phase |
| **Client portal** | portal.adawygroup.com — orders across all sub-brands, brand assets, invoices, structured intake, AI assistant | <Badge tone="planned">Phase 2</Badge> the flagship |
| **Employee portal** | One internal home: internal AI assistant, search across all company systems, operational dashboards, content engine | <Badge tone="planned">Phase 3</Badge> |
| **AI solutions** | Member-facing assistants and lead scoring; internal assistant, search, content engine, manufacturing intelligence | <Badge tone="planned">Phases 2–3</Badge> |

Everything below Phase 1 is **direction, not built code**. Nothing in the org
today runs NestJS, Prisma, Meilisearch or pgvector — those are choices
recorded in advance on [Tech Stack & Why](/architecture/tech-stack), not
dependencies you will find in a repository. **Better Auth is the one
exception**: the content dashboard below runs it for its own logins, which
makes it the first piece of the Phase-2 auth choice to exist in code.

## Department tooling

| System | What it is | Status |
| ------ | ---------- | ------ |
| **Content dashboard** ([`adawy-dashboard`](/repositories/adawy-dashboard)) | `admin.adawygroup.com`. Anyone with a login — an **admin** or a **content creator** — picks a site, edits its Arabic and English text or swaps an image, and presses Publish. A publish is **one git commit** to that site's own repository, made by a GitHub App, and the site's normal deploy takes it live ([ADR-014](/architecture/adrs)). Next.js 16, Better Auth (invite-only), Neon Postgres for logins only, Resend for invite and reset emails | <Badge tone="building">Practice mode</Badge> online since 27 September 2026 |
| **Practice content repo** ([`adawy-content-sandbox`](/repositories/adawy-content-sandbox)) | Where the online dashboard publishes while it is in practice mode — a folder per site, never deployed | <Badge tone="live">Running</Badge> until go-live |

The dashboard has three content stores, chosen by one environment variable,
`CONTENT_STORE`:

| Mode | Publishes to | Used |
| ---- | ------------ | ---- |
| `local` (the default) | A git repo per site in the clone's own `.sandbox/` folder | On a developer's machine — a fresh clone cannot publish anywhere real |
| `github-sandbox` | `adawy-content-sandbox` on GitHub | Online today, so the team can practise on the real screens |
| `github` | Each site's own repository | After go-live ([the roadmap](/architecture/roadmap#what-is-next-in-the-short-term)) |

The WordPress sites are not edited through it: their cards open each site's
own `wp-admin`, because a second way to edit the same content would be a second
source of truth.

## What runs where

| On Vercel (frontend) | On the backend host (Railway → DigitalOcean) |
| -------------------- | -------------------------------------------- |
| All brand websites — one Vercel project per app | Authentication and sessions |
| The content dashboard (`admin.adawygroup.com`) | |
| SSR and static generation | Business logic and Odoo integration |
| Client portal UI | Background jobs and scheduled tasks |
| Image optimization | Real-time connections (Pusher) for the portal |
| Preview deployments per PR (affected apps only) | Webhooks from Odoo |

The split exists because Vercel functions can't hold persistent connections
and time out on long-running jobs — fine for serving pages, wrong for Odoo
webhooks and queues. PostgreSQL runs managed (Supabase or Neon); Redis on
Upstash. The backend column is still a plan; the one managed database that
exists today is the dashboard's login store, a Neon Postgres database added
through the Vercel Marketplace.

Two client sites run on neither column: **aladawyshop.com** (WordPress + WooCommerce) and
**aladawypack.com** (WordPress) run on the Verpex host's cPanel
([below](#the-client-sites-that-stay-on-wordpress)).

## Odoo — the system of record

The group runs on **Odoo** for accounting, payroll, inventory, supply chain,
HR, and manufacturing. **We keep it permanently** and build custom layers on
top through its APIs. Commodity functions (payroll, tax compliance) are not
where we differentiate; client experience, dashboards, and AI are.

Flow example (hypothetical — no brand takes orders online yet): a client
orders on a Group brand site → the backend writes the order to Odoo → Odoo handles inventory, accounting, fulfilment → the client sees
status in the portal, surfaced from Odoo via our cache. Odoo's current API is
deprecated in Odoo 22 (late 2028), so the integration sits behind an
abstraction layer — migrating is one or two sprints, not a rewrite.

## The legacy system (what we are replacing, and why)

| Site | Old stack | Verdict from the technical audit |
| ---- | --------- | -------------------------------- |
| adawygroup.com | WordPress 6.9 + Semplice page builder, on the Verpex reseller host | Lighthouse mobile ~32; 4K background videos; stock photography; CMS-default page titles; no meta/OG tags; no structured data; English only. 20 documented findings. **Retired 21 September 2026**, when the domain moved to `apps/group` on Vercel; its old URLs redirect to their new pages. |

The audit's conclusion — accepted by leadership — was that this is a problem
of **platform fit, not execution**: no amount of WordPress optimization makes
a page-builder deliver the cinematic, bilingual, brand-driven experience the
group's positioning requires. Hence the rebuild ([ADR-002](/architecture/adrs)).

## The client sites that stay on WordPress

The same verdict first drove Next.js rebuilds of the two Aladawy client sites
([`aladawy-pack`](/repositories/aladawy-pack),
[`aladawy-shop`](/repositories/aladawy-shop)), which still run on
`*.vercel.app`. For these two the decision then went the other way: the
domains **stay on WordPress**, with the department's own code replacing the old
theme ([ADR-015](/architecture/adrs)). The shop's rebuild design states the
reason — the business keeps managing its products and orders in `wp-admin`,
the tool its staff already use — which is the difference from adawygroup.com,
where the department itself edits the site. Aladawy Pack followed on
26 September 2026; its reasoning is not yet written down anywhere.

| Site | What runs | State |
| ---- | --------- | ----- |
| aladawyshop.com | WordPress + WooCommerce with the department's `aladawy` theme and `aladawy-core` plugin ([`aladawy-shop-wp`](/repositories/aladawy-shop-wp)): bilingual Arabic/English, quote request, cash on delivery where a delivery fee is set, customer accounts. Built and tested on `staging.aladawyshop.com`, a password-protected copy, and released to live as uploaded plugin and theme zips | <Badge tone="live">Live</Badge> since 24 September 2026 |
| aladawypack.com | WordPress with the department's `aladawy-pack` theme ([`aladawy-pack-wp`](/repositories/aladawy-pack-wp)), ported from the Next.js build — site text under Appearance → Site content, products, and an Enquiries screen for the site's forms. Deployed by a script through the cPanel API, with no staging copy | <Badge tone="live">Live</Badge> since 26 September 2026 |

Both are **client deliverables, not Group systems**, so the detail lives under
[Repositories](/repositories). They also sit outside most of this handbook's
pipeline: no Vercel, no pull-request previews — see
[Deployment](/how-we-work/deployment#wordpress-sites-deploy-through-staging).

The Verpex host outlives the sites it served. It still runs every group
domain's DNS and most of the group's email, and that is deliberate
([Domains, DNS & Email](/architecture/domains-and-email)).
